1The core ideas

Spring Boot looks like magic until you see that it does four ordinary jobs: it creates your objects, hands them to each other, configures common libraries from what it finds, and routes each HTTP call to one of your methods.

The container creates your objects

Every class marked @RestController, @Service, @Repository or @Component becomes a bean: Spring creates one instance at startup and keeps it in the ApplicationContext. Beans are singletons by default, so the servlet-project problem of two servlets holding two different repositories cannot happen.

Dependency injection hands them over

A bean declares what it needs in its constructor; Spring finds the matching bean and passes it in. The framework calls your code instead of your code assembling the framework. That reversal is inversion of control.

Annotations are labels, and something reads them

An annotation does nothing by itself. It is metadata that one specific library looks for, either once at startup or on every call.

Auto-configuration fills the gaps

For each common library Boot carries a rule: if the jar is on the classpath (pom.xml), and the settings it needs exist (application.properties), and you have not defined that bean yourself, then create a sensible default.

postgresql jar+spring.datasource.url+no DataSource of yours=HikariCP pool, 10 connections

Define your own bean of the same type and Boot steps back. That is what “opinionated defaults” means in practice: every default can be replaced.

The frontend renders the view

@RestController is @Controller plus @ResponseBody: whatever the method returns is written into the response body as JSON, instead of being treated as the name of a template.

DispatcherServlet is the front controller. In the servlet project you mapped one servlet per URL. Spring MVC registers a single DispatcherServlet for every URL and routes internally to your @GetMapping and @PostMapping methods. It still lives the same servlet lifecycle (init, service, destroy) inside an embedded Tomcat.

    4From @Entity to a table

    An @Entity class is a description of a table written in Java. At startup Hibernate reads its annotations and, depending on ddl-auto, turns them into a CREATE TABLE. Click a line on either side to see how it maps.

    DDL Hibernate generatesPostgreSQL

    Hibernate 6 may print the columns in a different order from the fields (it groups them by type). Column order has no effect on how SQL works.

    spring.jpa.hibernate.ddl-auto: what Hibernate does to the schema

    This one property decides whether your tables survive a restart. ddl-auto only ever goes from Java to the database: it creates tables from classes, never classes from tables.

    5Who writes the SQL

    Your service calls a repository method and a SQL statement reaches PostgreSQL. Four libraries sit between those two points, and each has exactly one job.

    The one-line mental model. JPA is to Hibernate what List is to ArrayList. JPA (jakarta.persistence) is the specification: annotations, the EntityManager interface and the JPQL query language, with no code that talks to a database. Hibernate is the implementation that generates and runs SQL. Spring Data JPA sits on top and writes the repository class for you.

    Pick a call and read down the pipeline. Notice where the language changes: Spring Data and JPA speak in classes and fields (Movie, m.releaseYear); from Hibernate down it is tables and columns (movies, release_year).

    6@Repository and its built-in methods

    Three lines give you more than 25 working data-access methods. The two type arguments tell Spring Data which entity the repository manages and the Java type of its @Id.

    Where the methods come from

    • Repository<T, ID>marker: tells Spring Data “build an implementation of this”
      • CrudRepositorysave, saveAll, findById, existsById, findAll, findAllById, count, deleteById, delete, deleteAll
        • ListCrudRepositorythe same methods, returning List instead of Iterable
      • PagingAndSortingRepositoryfindAll(Sort), findAll(Pageable)
        • ListPagingAndSortingRepositoryfindAll(Sort) returning List
    • QueryByExampleExecutorfindAll(Example): query by a sample object
    • JpaRepository<T, ID>combines the three List interfaces above and adds flush, saveAndFlush, saveAllAndFlush, deleteAllInBatch, getReferenceById
      • MovieRepositoryyours: inherits everything above, plus the custom methods you add
    Where is the implementation class? You never write MovieRepositoryImpl. At startup Spring Data creates a proxy object that implements your interface and forwards every built-in call to SimpleJpaRepository<Movie, Long>, a real class inside the spring-data-jpa jar. Print movieRepository.getClass() and you will see a generated name such as jdk.proxy2.$Proxy118.
    Is @Repository required here? No. Extending JpaRepository is enough for Spring Data to find the interface; teams often keep the annotation as documentation. On a hand-written DAO class (like your HashMap repository) @Repository does real work: it registers the bean and translates raw SQLExceptions into Spring’s DataAccessException family.

    How save() decides between INSERT and UPDATE

    movieRepository.save(movie)
    ↓
    Is movie.getId() null?
    Yes: a new movie
    entityManager.persist(movie)
    ↓
    INSERT right away (IDENTITY needs the id now); the id is written back into the same object
    No: an existing movie
    entityManager.merge(movie)
    ↓
    Already loaded in this transaction?
    Yes: no SELECT
    No: SELECT by id, then copy your values onto it
    ↓
    UPDATE at commit, and only if a value actually changed (dirty checking)

    This is why the update in section 8 loads the movie with findById first: the 404 check happens up front, and the later save() needs no second SELECT. It is also why the id should be a wrapper type (Long): null is how Spring Data recognises a new object.

    Derived name@Query JPQL@Query nativeSpecification
    EffortLowest: just a nameMediumMediumHighest: extra classes

    Recommendation. Use derived names for one or two conditions. Move to JPQL when the name stops reading like a sentence. Reach for native SQL only for something JPQL cannot express, and for Specifications when users can combine optional filters. Any @Modifying query needs a transaction and skips the persistence context, so objects already loaded in the same transaction keep their old values unless you set clearAutomatically = true.

    8@Service: the business rules

    The service is where StreamHub’s rules live: a title is required, ratings run from 0 to 10, titles are unique. It calls the repository, knows nothing about HTTP, and draws the transaction boundary.

    The rule pipeline inside createMovie()

    validate(movie)fails: InvalidMovieException, 400
    →
    existsByTitleIgnoreCase()true: DuplicateMovieException, 409
    →
    save(movie)INSERT, id generated
    →
    return savedcontroller answers 201

    The cheapest check runs first: validation needs no database, so an invalid movie costs zero SQL statements. Watch the Create, Invalid rating scenario in the visualizer to see it.

    Why it is written this way

    ChoiceWhyTrade-off
    Interface plus implementationThe controller depends on MovieService, so tests can mock it, and Spring can wrap the implementation in a transaction proxy.One more file. Many teams skip the interface when only one implementation will ever exist.
    Constructor injection into a final fieldThe dependency can never be null or replaced later, and a unit test can pass a fake with plain new.None worth worrying about. Field injection with @Autowired is the older style.
    @Transactional on service methodsOne business operation is one transaction, even when it makes several repository calls (exists check, then save).A pooled connection is held for the whole method, so keep slow work such as HTTP calls outside it.
    readOnly = true on readsHibernate skips change tracking for the objects it loads.Changes made inside a read-only method are silently not written.
    Exceptions extend RuntimeException@Transactional rolls back on unchecked exceptions by default.A checked exception commits unless you add rollbackFor.
    Throws domain exceptions, never returns ResponseEntityThe same service can serve REST, a scheduled job or a message listener.Someone must map each exception to a status: the controller here, a @RestControllerAdvice in industry.
    Two @Transactional traps. Import org.springframework.transaction.annotation.Transactional; the jakarta.transaction version has no readOnly. And a call from one method to another inside the same class skips the proxy: when updateMovie() calls getMovieById(), that inner readOnly is ignored. Here that is exactly right, because the outer write transaction is already open.

    9@RestController: the HTTP edge

    The controller translates between HTTP and Java and nothing else. Every part of a request maps to one annotation; click a part to see which.

    Mapping annotations and the status each should return

    AnnotationUse it toRequest bodySuccessSame result if repeated?
    @GetMappingRead one or manyNone200 OKYes
    @PostMappingCreateThe new movie201 CreatedNo: each call creates another row
    @PutMappingReplace the whole movieEvery field200 OKYes
    @PatchMappingChange some fieldsOnly the changed fields200 OKUsually
    @DeleteMappingRemoveNone204 No ContentYes (the second call gets 404, the state is the same)
    Things Spring answers before your code runs. /api/movies/abc cannot become a Long, so the response is 400. A missing ?title= on /search is 400. Malformed JSON is 400. A wrong verb, such as PATCH on an endpoint that has none, is 405 Method Not Allowed.
    Why @CrossOrigin is there. React (port 3000) and Angular (port 4200) run on a different origin from port 8080, so the browser blocks their calls unless the server allows them. The annotation is the quick fix; in Phase 3 this moves into one CORS configuration alongside Spring Security.

    11How teams build it

    Everything above is how Spring Boot works. This section is how professional teams arrange the same pieces, and what each upgrade costs.

    The order a team builds a new CRUD feature

    1. Agree the API contract. URL, request and response JSON, status codes, often written as an OpenAPI file that the React and Angular developers review.
    2. Write the migration. V3__create_movies.sql in src/main/resources/db/migration, run by Flyway. The schema is versioned in Git like code.
    3. Map the entity. Movie mirrors that table; ddl-auto=validate fails startup if the two disagree.
    4. Add the repository. Extend JpaRepository; add custom queries only when a use case needs them.
    5. Define DTOs and a mapper. MovieRequest and MovieResponse as Java records, with validation annotations on the request.
    6. Write the service and its unit tests. Business rules plus @Transactional, tested with Mockito and no database.
    7. Write a thin controller. @Valid on the request body, tested with @WebMvcTest and a mocked service.
    8. Register error handling. New exceptions get a mapping in the shared @RestControllerAdvice.
    9. Open a pull request. CI (GitHub Actions, Phase 4) builds and runs every test; a reviewer approves; the branch merges.

    Package layout: two options

    Option A matches most tutorials and makes each layer easy to find while you are learning. Option B keeps everything about one feature in one folder, which makes it far easier to split the monolith into Auth, Content and User services in Phase 5. A reasonable path: start with A, and switch to B once StreamHub has three or more features.

    Defaults worth knowing

    200Tomcat worker threads at most server.tomcat.threads.max
    10HikariCP connections in the pool spring.datasource.hikari.maximum-pool-size
    30 swait for a free connection before an error …hikari.connection-timeout
    20default page size for Pageable parameters (maximum 2000)
    8080default port server.port

    Read the first two together: up to 200 requests can run at once, but only 10 can hold a database connection. A slow query or a long transaction keeps a connection busy; once all 10 are taken, every other request waits, for up to 30 seconds. That single fact explains why teams keep transactions short and never call another web service from inside @Transactional.
