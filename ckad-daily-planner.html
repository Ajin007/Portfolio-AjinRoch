Spring Boot to CKAD, Thursday to exam day

19 November 2026 to 31 January 2027, around two leave breaks with no study: 24 December to 1 January and 13 to 17 January. Weekdays are 90 minutes, weekends 3 hours. Five checkpoints, one per official domain, add up to a weighted readiness score in the Scores tab. Exam on Saturday 30 January.

Official weightage, and where your marks stand

The five domains and their weights below are the Linux Foundation’s official CKAD curriculum. The pass mark is 66%. Each checkpoint in your plan tests one domain; enter your score after it and this page weights it exactly as the exam does.

killer.sh scores

killer.sh is deliberately harder than the exam and scores the whole paper, not one domain, so it isn’t mixed into the weighted number. Common experience is that 50 to 60% there means you’re ready; under 40% means more drilling.

How to score a checkpoint

  • Score each task 1 if it’s fully right, ½ if a multi-part task is partly right, 0 otherwise. The real exam is graded automatically on the state of the cluster, so a typo in a name or the wrong namespace scores like a missing answer.
  • Domain score = points ÷ number of tasks. Enter it as a percentage.
  • Weighted readiness = 0.20 × design and build + 0.20 × deployment + 0.15 × observability + 0.25 × configuration and security + 0.20 × networking.
  • Points at risk = domain weight × the share you missed. Missing 40% of configuration and security costs 10 exam points; missing 40% of observability costs 6. Spend gap-fixing time in that order.
  • The Linux Foundation doesn’t publish points per task, and tasks differ in size. The task counts in the table are the weights applied to a 15 to 20 task paper, so treat them as estimates.

What to learn, and what you already know

Each topic below is on the CKAD curriculum. The teal line under a topic is the Spring Boot or Docker idea you already have that maps onto it, so you can learn the Kubernetes version by analogy. Tick a topic once you can do it in under 6 minutes without notes.

Skip: you already have this

  • Writing Dockerfiles, multi-stage builds, image tags
  • Docker CLI basics: build, run, logs, exec, ps
  • Microservice architecture and REST
  • YAML and JSON syntax
  • HTTP health endpoints (Actuator)
  • Profile and environment-based configuration

Don’t study: not on CKAD

  • Cluster install with kubeadm, upgrades
  • etcd backup and restore
  • Node, kubelet and control-plane troubleshooting
  • CNI plugin internals
  • Gateway API (its docs are allowed only in the CKA)
  • Service mesh, writing Operators in Go

Where to experiment, and how to set it up

Everything here is free except killer.sh, which comes with the exam. Your main lab is the Killercoda Kubernetes playground: it runs in the browser, so your corporate laptop’s AppLocker rules don’t matter.

1. Killercoda Kubernetes playground

Main lab for almost every day.

  1. Open the playground and sign in with GitHub or Google.
  2. Press Start. In about a minute you get a terminal on controlplane with a 2-node cluster.
  3. Paste the shell setup block below.
  4. Free sessions last about an hour and reset when they end, so commit YAML to your ckad-lab repo before the timer runs out.

2. Killercoda Ubuntu playground

Image builds on days 3 and 11.

  1. Open the Ubuntu playground and press Start.
  2. Docker is there. Check with docker version.
  3. Add podman: sudo apt-get update && sudo apt-get install -y podman.
  4. Clone your Spring Boot repo and build with both tools.

3. Killer Shell CKAD scenarios

Guided tasks with an automatic check. Use alongside the plan from 27 November, and sweep them all on 21 January.

  1. Open the Killer Shell CKAD list.
  2. Pick the scenario matching today’s topic.
  3. Solve it, then press Check. Read the solution only after a real attempt.

4. Question banks on GitHub

Task lists you run inside the playground.

  1. CKAD-exercises: open the file for the topic (core concepts, multi-container, pod design, configuration, observability, services, state, helm, CRD).
  2. ckad-crash-course: exercises folder, numbered, with solutions.
  3. ckad-killer.sh: clone it for extra mixed practice in the final stretch.

5. Local cluster (optional)

Only if you want to work offline. Not needed.

  1. Docker Desktop: Settings, Kubernetes, Enable Kubernetes.
  2. Or kind: put kind.exe and kubectl.exe in a folder under C:\Program Files\ and add it to PATH, then kind create cluster.
  3. If AppLocker blocks either, stop there and stay on Killercoda.

6. killer.sh simulator

9 to 10 January and 23 to 24 January. Comes with the exam purchase.

  1. LF portal (trainingportal.linuxfoundation.org), Start/Resume, exam checklist, Preparing for the exam.
  2. Each of the 2 sessions gives 36 hours of access from activation and 17 questions.
  3. Activate only when you have 2 clear hours, then review within the window.

Practice project: event-driven order saga on Kubernetes

piomin/sample-spring-kafka-microservices: three Spring Boot services on Java 21. order-service publishes Order events to Kafka, payment-service and stock-service each run a local transaction and reply, and order-service joins the replies with Kafka Streams to confirm or roll back (the saga pattern). The repo runs on Docker Compose but ships no Kubernetes manifests, so writing them is your practice.

Your plan has optional project steps on 22 days, marked P1, P2… inside each day. . The exam never asks about Kafka, so cap each project session at 40 minutes and skip it on a busy day.

One Dockerfile for all three services (repo root)

FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /src
COPY . .
ARG MODULE=order-service
RUN mvn -q -pl ${MODULE} -am package -DskipTests

FROM eclipse-temurin:21-jre
ARG MODULE=order-service
COPY --from=build /src/${MODULE}/target/*.jar /app/app.jar
USER 1000
ENTRYPOINT ["java","-jar","/app/app.jar"]

# docker build --build-arg MODULE=payment-service -t <you>/payment-service:v1 .

Single-node Kafka for the playground (KRaft, no ZooKeeper)

apiVersion: apps/v1
kind: Deployment
metadata: {name: kafka, namespace: saga}
spec:
  replicas: 1
  selector: {matchLabels: {app: kafka}}
  template:
    metadata: {labels: {app: kafka}}
    spec:
      containers:
      - name: kafka
        image: apache/kafka:3.8.0
        ports: [{containerPort: 9092}]
        env:
        - {name: KAFKA_NODE_ID, value: "1"}
        - {name: KAFKA_PROCESS_ROLES, value: "broker,controller"}
        - {name: KAFKA_LISTENERS, value: "PLAINTEXT://:9092,CONTROLLER://:9093"}
        - {name: KAFKA_ADVERTISED_LISTENERS, value: "PLAINTEXT://kafka:9092"}
        - {name: KAFKA_CONTROLLER_LISTENER_NAMES, value: "CONTROLLER"}
        - {name: KAFKA_LISTENER_SECURITY_PROTOCOL_MAP, value: "CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT"}
        - {name: KAFKA_CONTROLLER_QUORUM_VOTERS, value: "1@localhost:9093"}
        - {name: KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR, value: "1"}
        - {name: KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR, value: "1"}
        - {name: KAFKA_TRANSACTION_STATE_LOG_MIN_ISR, value: "1"}
        - {name: KAFKA_HEAP_OPTS, value: "-Xmx512m -Xms512m"}
---
apiVersion: v1
kind: Service
metadata: {name: kafka, namespace: saga}
spec:
  selector: {app: kafka}
  ports: [{port: 9092}]
  • Memory: Kafka plus three JVMs is heavy for a free playground. Keep 1 replica each and small heaps; if Pods stay Pending or get OOMKilled, run Kafka with one service at a time.
  • A Deployment is fine for practice. In production Kafka runs as a StatefulSet or through an Operator such as Strimzi, which is a good example to read on CRD day.
  • Lighter alternative: piomin/sample-message-driven-microservices uses RabbitMQ with Spring Cloud Stream (Java 21, Boot 3.5). Same steps, smaller broker, but no Kafka Streams.

Practice tasks in exam style

The real exam has 15 to 20 tasks in 2 hours, about 7 minutes each. Set a timer, solve in a Killercoda playground with only kubernetes.io and helm.sh open, then compare with the solution.
