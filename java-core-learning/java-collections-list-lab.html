List — ArrayList vs LinkedList, drawn from the inside

An ArrayList is a resizable array; a LinkedList is a chain of nodes. Every claim about which is faster comes from that one sentence — so this page draws the actual backing array with its spare capacity, and the actual node chain with its prev/next pointers, and then counts the work each operation costs. No hand-waving about Big-O.

Overview

One set of interfaces, many implementations

Before collections, Java had arrays (fixed size) and Vector/Hashtable (unrelated APIs). The Collection Framework, added in Java 1.2, put one contract in front of every data structure: learn add, remove, size, iterator once and every implementation obeys it. Swapping an ArrayList for a LinkedList then becomes a one-word change.

Interfaces

What a collection promises — List, Set, Queue, Map. You program against these.

Implementations

How the promise is kept — ArrayList, LinkedList, HashSet, HashMap. You choose one by cost.

Algorithms

Static helpers that work on any of them — Collections.sort, reverse, max, shuffle, unmodifiableList.

Generics, autoboxing and the two rules

 basics.java
Collections hold objects, never primitives

List<int> does not compile. You write List<Integer> and Java autoboxes each int into an Integer object. That is why a list of a million numbers costs far more memory than int[1000000] — and why remove(1) on a List<Integer> removes index 1, while remove(Integer.valueOf(1)) removes the value 1.

List

An ordered collection that allows duplicates

Two promises define List: every element has an integer index from 0 to size−1, and duplicates are allowed. Everything else — array or nodes, fast or slow — is the implementation's business.

ArrayList

A resizable array — and "resizable" is a polite fiction

Inside every ArrayList is a plain Java array called elementData. Arrays cannot grow, so when it fills up the list allocates a bigger one and copies everything across. That is the whole design, and it explains every performance characteristic below.

  • size = how many elements you put in. capacity = how many the current array can hold. They are not the same, and only size() is visible to you.
  • A new ArrayList<>() starts with a shared empty array and jumps to capacity 10 on the first add.
  • Growth is newCap = oldCap + (oldCap >> 1) — half again. So 10 → 15 → 22 → 33 → 49 → 73 …

💡 If you know the size, say so

new ArrayList<>(1000) allocates once. Without it, filling 1000 elements triggers about ten grow-and-copy cycles. Press add 12 quickly above and watch capacity go 10 → 15 with a 10-element copy.

remove() does not shrink the array

Capacity never falls on its own. A list that held a million elements still owns a million-slot array after clear(). trimToSize() is the only way back — try it above.

LinkedList

A chain of nodes — no array, no capacity, no copying

A LinkedList stores each element in its own Node object holding three references: prev, item, next. The list itself only remembers first and last. Nothing is contiguous, nothing is ever copied — but nothing can be reached by arithmetic either. To get element 7 you must walk to it.

It is doubly linked, which is why node(index) starts from whichever end is closer: if (index < (size >> 1)) walk forward, else walk backward. Worst case is the middle.

⛔ The classic disaster

for (int i = 0; i < list.size(); i++) list.get(i); over a LinkedList is O(n²) — each get walks again from an end. Over 10 000 elements that is roughly 25 million pointer hops instead of 10 000. Use a for-each loop or an Iterator, which walks once and remembers where it is.

LinkedList is also a Deque

It implements Queue and Deque as well as List, so you get offer, poll, peek, push, pop for free. That — not indexed access — is what it is genuinely good at. For a pure queue, ArrayDeque is faster still.

✓ The practical rule

Default to ArrayList. Reach for LinkedList only when you are repeatedly adding or removing at the ends — and if that is all you need, ArrayDeque beats both. Real-world code uses ArrayList the overwhelming majority of the time, because CPU caches love contiguous memory and hate pointer chasing.

Why the middle-insert result surprises people

"Linked lists are fast at inserting in the middle" is true only if you already hold the node. Through the List API you do not — you pass an index, so the list must walk there first. The relinking is O(1); the walking is O(n).

 where LinkedList genuinely wins

With a ListIterator you keep the position between operations, so no walking is repeated. That is the case the textbook claim is really about.

Iteration

Four ways to walk a list, and one way to crash

Every collection can hand you an Iterator — a cursor with three methods: hasNext(), next(), remove(). The for-each loop is just syntax sugar over it, which is why the two share the same fatal trap.

⛔ ConcurrentModificationException

Every list keeps a modCount that ticks on every structural change. An iterator snapshots it and re-checks on each next(). Call list.remove(...) during a for-each and the counts diverge — the iterator throws immediately, and the word "Concurrent" is misleading: this happens on a single thread.

Your code

From one Gsec to a List<Gsec>

Your Main holds exactly one student in one variable. A college has thousands. The moment you write Gsec s1, s2, s3… you have outgrown variables and need a collection — and every method you wrote (getAge, validator, display) keeps working unchanged on every element.

💡 What a List changes about your class
  • private int age → sorting and filtering must go through getAge(). Encapsulation survives.
  • validator() → runs in a loop over every element; one method, whole batch checked.
  • display() prints "Hi sreekanth" for everyone — a list makes that hardcoded name impossible to miss.
  • No toString() → printing the list shows Gsec@1b6d3586. Adding one fixes every print at once.
  • No equals() → contains() and remove(Object) compare references and silently fail.
