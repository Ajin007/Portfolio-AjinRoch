Concept

One program, several things happening at once

A thread is a single path of execution inside a program. Every Java program already has one — the main thread — and multithreading simply means starting more of them so that independent work does not have to queue up behind a slow task.

Why bother

  • Responsiveness. A file download no longer freezes the interface, because the download runs on its own thread.
  • Utilisation. While one thread waits on disk or network, another gets the CPU instead of it sitting idle.
  • Parallelism. On a multi-core machine, genuinely separate threads run at the same instant on different cores.
  • Cheap. Threads share one memory space, so creating one costs far less than starting another process.

And the price you pay

  • Shared memory is shared trouble. Two threads updating one variable can lose updates — tab ⑤ makes this happen for real.
  • The order is not yours to choose. The JVM scheduler decides. The same program prints different output on different runs.
  • New failure modes. Deadlock, starvation, and bugs that appear once in a thousand runs.

Concurrency ≠ parallelism

Concurrency is dealing with many tasks by interleaving them — one core, rapid switching. Parallelism is doing many tasks at the same instant on several cores. Java gives you threads; the JVM and the OS decide which of the two you actually get.

start() vs run() — the question that ends most vivas

Calling run() directly is legal Java. It just is not multithreading: it is an ordinary method call on the current thread.

✓ Prefer Runnable

Extend Thread only when you genuinely need to override thread behaviour itself. Otherwise Runnable keeps what to do separate from who does it — and it is the form every modern API expects.

Two more things the compiler will not let you do

  • start() twice on one object → IllegalThreadStateException at runtime. A dead thread cannot be restarted; create a new one.
  • run() cannot declare checked exceptions — the interface method does not, so an override cannot widen it. Catch inside, or wrap in a RuntimeException.

⛔ sleep() does not release the lock

This is the single most-asked comparison. Thread.sleep() pauses the thread but keeps every monitor it holds, so anyone waiting on that lock stays BLOCKED. wait() is the opposite: it releases the monitor so another thread can make progress. Sleeping inside a synchronized block is therefore an easy way to strangle your own program.

join() — the only way to guarantee an order

Without join() the main thread races ahead and prints its summary before the workers finish. With it, main waits. Toggle the checkbox and compare.

setPriority() — a hint, not a promise

Three threads with priorities 1, 5 and 10, doing identical work. The panel counts how many CPU slices each one actually received.

Do not build logic on priority

The JVM maps Java priorities onto whatever the host OS offers, and some platforms collapse them entirely. A priority-10 thread may still finish last. Priority tunes performance; it never establishes correctness. If you need an order, use join() or a lock.

Synchronization

count++ is three operations, and that is the whole problem

What looks like one statement compiles to read the value → add one → write it back. If a second thread reads between your read and your write, both threads write the same number and one increment vanishes. This is a race condition, and the region of code where it can happen is the critical section.

 why count++ is not atomic

The race, actually happening

Two threads, five increments each, so the correct answer is 10. Run it. The trace marks every lost update — a write that stored a value another thread had already stored.

The fix — one monitor, one thread at a time

Every Java object owns a hidden monitor. synchronized makes a thread acquire it before entering and release it on the way out — including when an exception is thrown. Anyone else arriving meanwhile goes BLOCKED.

 three ways to synchronize
FormLock taken
synchronized methodthis — the whole object
synchronized static methodClassName.class — one lock for all instances
synchronized(obj) { }whatever object you name — the finest control
Prefer the narrowest block

A synchronized method locks for its entire duration. If only three lines touch shared state, wrap only those three in a block — everything else keeps running in parallel. Locking too much turns a multithreaded program back into a sequential one.

Two objects, two locks

A synchronized instance method protects that instance. Two threads working on two different objects never contend — which is correct, and also why a shared counter must live in one shared object.

Deadlock — both polite, both stuck

T1 takes lock A then wants B. T2 takes B then wants A. Neither will let go. The simulator detects the moment every thread is BLOCKED and nothing can ever proceed.

✓ The standard cure: lock ordering

Make every thread acquire locks in the same global order — always A before B. Then a cycle cannot form. Other options: a single coarser lock, or tryLock() with a timeout from java.util.concurrent.locks.

wait() / notify() — the producer & consumer

Locks stop threads colliding; they do not let threads wait for a condition. That is what wait() and notify() add. A buffer holding one item forces strict alternation.

⛔ Three rules that are always tested

1 · wait(), notify(), notifyAll() belong to Object, not Thread. 2 · They may only be called while holding that object's monitor — otherwise IllegalMonitorStateException. 3 · Always wait in a while loop, never an if: a woken thread must re-check the condition, because another thread may have consumed it first.

Quick answers

  • sleep vs wait — sleep is static and keeps the lock; wait is on Object and releases it.
  • start vs run — start creates a new stack; run is an ordinary call on the current thread.
  • notify vs notifyAll — one arbitrary waiter vs every waiter; prefer notifyAll unless you can prove one is enough.
  • synchronized vs volatile — volatile guarantees visibility of a variable, not atomicity of an update; count++ stays broken with volatile alone.
  • Why is Runnable preferred? It leaves the inheritance slot free and works with thread pools.
  • Can a thread be restarted? No — a second start() throws IllegalThreadStateException.
  • What is a daemon thread? A background thread the JVM will not wait for on exit.
