Pillar 2

Polymorphism — one name, many forms

Java gives you two flavors. Compile-time (static): the compiler picks which method by looking at the parameter list → overloading. Runtime (dynamic): the JVM picks which method by looking at the actual object → overriding. Your commented-out no-arg constructor is the overloading half; we add a Student subclass for the overriding half.

Why each mechanism is polymorphism

  • Overloading (compile-time): Gsec() and Gsec(String,String,int,int) share one name; the argument list you write selects the winner before the program ever runs. Same for methods: setAge(int) vs a hypothetical setAge(String).
  • Overriding (runtime): Gsec ref = new Student(); → the reference says Gsec, the heap object says Student → ref.display() runs Student's version. That decision is made at runtime by the JVM's virtual-method table.
  • Rule of thumb: reference type decides what you may call; object type decides which body runs.
@Override matters

Always annotate overrides with @Override. If you typo the signature (e.g. Display()), the compiler screams instead of silently creating an unrelated method.

Inheritance — reuse a parent, specialize in a child

A child class acquires the fields and methods of its parent with extends. Java allows single and multilevel inheritance with classes, but bans multiple class inheritance (the diamond problem) — and that's exactly the hole that interfaces fill. Click each diagram node.

How "multilevel inheritance using an interface" actually works

  • Level chain with interfaces: interface Person → interface Learner extends Person → class Gsec implements Learner. Gsec must satisfy the whole chain — both breathe() and study(). That is multilevel inheritance of type & contract.
  • An interface may extend MANY interfaces (interface Learner extends Person, Coder) — legal, because interfaces carry no state to collide.
  • A class may implement MANY interfaces while still extending one class: class Student extends Gsec implements Sports, Placement — Java's answer to multiple inheritance.
  • Diamond with default methods? If two interfaces give the same default method, the class is forced to override and may pick one via Person.super.intro() — ambiguity resolved explicitly, never silently.
Pillar 4

Abstraction — expose the what, hide the how

Encapsulation hides data; abstraction hides implementation. Callers of validator() shouldn't care whether eligibility is "age ≥ 18" or a database rule — they just call it. *Footnote for interviews

Since Java 8, interfaces can carry default method bodies, so "interface = 100% abstraction" is only strictly true pre-Java 8. Say that out loud in a viva and watch the examiner smile.

Checked exceptions — "the compiler is your co-signer"

Definition: subclasses of Exception that are not under RuntimeException. They model failures in the outside world (files, networks, databases, threads) that can happen even in perfect code — so the compiler refuses to compile unless you either catch them or declare throws. Checked = checked at compile time.

Unchecked exceptions — "your bug, your 3 AM stack trace"

Definition: RuntimeException and all its children. They signal programming mistakes — broken assumptions that better code would prevent. Six rules to never forget

  • throw = the action (throws one object, inside a method). throws = the warning label (on the method signature, lists classes).
  • Catch child before parent — catch(Exception e) above catch(ArithmeticException e) is a compile error ("already caught").
  • finally always runs — even after return; skipped only by System.exit() or JVM death.
  • Multi-catch types must be unrelated (no parent|child pairs) and the variable is implicitly final.
  • Custom checked → extends Exception. Custom unchecked → extends RuntimeException.
  • e.getMessage() prints just the message; e.toString() = class name + message; printStackTrace() = the full trail. Output-format questions love this trio.
