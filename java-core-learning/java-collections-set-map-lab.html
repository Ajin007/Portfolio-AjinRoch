HashSet & HashMap — the bucket table, drawn live

A HashSet is a HashMap wearing a disguise, and a HashMap is an array of buckets plus one arithmetic trick. This page draws that array: type a key and watch hashCode() get spread, folded into a bucket index, collide with a neighbour, and eventually trigger a resize. Then it counts what a Map lookup costs against a List scan on the same data — which is the real answer to "why a Map".

Set

A collection that refuses duplicates

Set adds no new methods to Collection. It only tightens one rule: an element that is already present is not added again, and add() returns false to tell you so. Everything interesting is in how each implementation decides what "already present" means.

HashSet

Hash table. No order at all. O(1) add / contains / remove. The default.

LinkedHashSet

Hash table + a linked list through the entries. Insertion order preserved, marginally slower.

TreeSet

Red-black tree. Sorted order, O(log n). Elements must be comparable.

Internals

An array of buckets, and one piece of arithmetic

A HashMap holds Node[] table — by default 16 buckets. Storing a pair takes three steps, and every performance claim about maps follows from them:

  1. Call key.hashCode() — a 32-bit int chosen by the key's class.
  2. Spread it: h ^ (h >>> 16). This mixes the high bits down, because step 3 would otherwise ignore them entirely.
  3. Fold it: index = (n - 1) & hash. With n a power of two this is a fast modulo — it simply keeps the low bits.

Two different keys can land in the same bucket. That is a collision, and the bucket becomes a small linked list — converted to a red-black tree once it passes 8 entries.

The numbers to memorise

default capacity16 buckets, always a power of two
load factor0.75 — the space/time compromise
thresholdcapacity × load factor = 12 for a new map
resizeat the 13th entry: capacity doubles to 32 and every entry is rehashed
treeifya bucket with 8+ entries becomes a red-black tree (if capacity ≥ 64)
worst caseall keys collide → O(n) before treeify, O(log n) after
💡 Why 0.75 and not 1.0?

A hash table only stays O(1) while buckets are mostly short. Waiting until the table is completely full guarantees long chains; resizing too early wastes memory. 0.75 is the measured sweet spot, and it means a HashMap is always at least 25% empty by design.

Order is not a promise, and it is not random either

Iteration follows bucket order, which depends on hash codes and on the current capacity. It looks arbitrary, it is perfectly deterministic, and it changes after a resize. Never rely on it — use LinkedHashMap or TreeMap if order matters.

Map

Key → value, and deliberately not a Collection

A Map stores pairs. Collection.add(E) takes one element, so a Map cannot implement it without lying — which is why Map sits outside the Collection branch of the hierarchy. It offers three views instead, and those views are Collections.

keySet()

A Set<K> of the keys — no duplicates, by definition.

values()

A Collection<V> — duplicates allowed, because two keys may share a value.

entrySet()

A Set<Map.Entry<K,V>> — the pairs themselves, and the only efficient way to iterate both at once.

They are views, not copies

map.keySet().remove(k) removes the entry from the map. Changes flow both ways. That is powerful and occasionally surprising.

⛔ get() returning null is ambiguous

null can mean "no such key" or "the key is there and its value is null". containsKey() is the only way to tell them apart. HashMap allows one null key and any number of null values; TreeMap and Hashtable allow no null key at all.

The case for Map

Because looking something up by name should not mean reading everything

Find student 104 in a List<Gsec> and you compare register numbers one at a time until you hit it — on average half the list. Find them in a Map<Integer,Gsec> and you do one hash calculation and land in the right bucket. Below, both run on the same data and the comparisons are counted.

✓ The one-line rule

If you ever find yourself writing a loop that searches a list for a match on one field — that field wants to be a map key.

And where it is the wrong answer

  • You need order or position. "The third student who registered" is a List question.
  • You search by value, not key. containsValue() is O(n) — a map gives you nothing there.
  • The data is tiny. For five elements a list scan beats hashing; the map only pays off as n grows.
  • You need every element in order every time. Iterating a HashMap is fine, but a List is simpler and cache-friendlier.
  • Duplicate keys are meaningful. A Map silently overwrites — put on an existing key replaces the old value and returns it.

The contract

Your Gsec class breaks a HashSet, and here is exactly how

A hash collection finds an element in two moves: hash to a bucket, then walk that bucket comparing with equals(). Your class overrides neither method, so it inherits Object's versions — hash based on the memory address, equality based on the memory address. Two students with the same register number therefore hash to different buckets and are never even compared.

⛔ The contract, in one line each

1 · If a.equals(b) then a.hashCode() == b.hashCode() — always.
2 · Equal hash codes do not imply equality; that is just a collision.
3 · Both must be computed from the same fields, and those fields should not change while the object sits in a set or map.

Why equals() alone is not enough

Without hashCode(), two equal objects get two different address-based hashes, so they land in different buckets. The set never puts them side by side, never calls your equals(), and stores both. Your override is correct and completely unused.

And hashCode() alone?

Both objects reach the same bucket — then the set compares them with the inherited address equality, decides they differ, and chains them. Same duplicate, one bucket instead of two.

The mutable-key trap

Put an object in a HashSet, then change a field its hashCode() depends on. The object now hashes to a different bucket than the one it is physically sitting in — contains() returns false for an object that is demonstrably inside the set, and remove() cannot find it either. Base hashCode() on fields that never change: for Gsec, that is registerNumber, never age.

Iterator

One cursor, every collection

Because Iterable sits at the top of the hierarchy, the same three methods walk a List, a Set, or any view of a Map. That uniformity is the whole point of the framework.

 iterating every collection type
MethodDoes
hasNext()is there another element? Never moves the cursor.
next()returns the next element and advances. NoSuchElementException if there is none.
remove()removes what next() just returned. The only safe removal during a walk. Calling it before next() throws IllegalStateException.
⛔ Maps have no iterator()

map.iterator() does not compile — a Map is not Iterable. You iterate one of its views: map.keySet(), map.values(), or map.entrySet(). Use entrySet() when you need both key and value — looping keys and calling get(k) inside does the hash lookup twice for every entry.
