String is immutable — everything else follows from that

Every surprising thing about Java strings comes from one design decision: a String object can never change. So s.toUpperCase() does not modify s, + in a loop builds garbage, == sometimes works and sometimes doesn't, and StringBuilder exists at all. This page draws the string pool and the heap, runs the real method algorithms character by character, models StringBuilder's capacity growth, and lays out every access-specifier rule as a grid you can click.

String class

Immutable, final, and pooled

java.lang.String wraps a private array of bytes (a char[] before Java 9) and marks it final. There is no method anywhere in the class that changes it — every method that looks like it modifies the string actually returns a brand-new one. The class itself is final too, so nobody can subclass it and break that promise.

Immutable

Safe to share between threads, safe as a HashMap key, and its hashCode() can be cached forever.

Pooled

Identical literals share one object in the string pool, so a program with a thousand "Dell" literals holds one "Dell".

Costly to edit

Building a string in a loop with + allocates a new object every iteration. That is what StringBuilder is for.

StringBuilder & StringBuffer

A mutable string, with spare room built in

Both classes hold a char[] that is deliberately larger than the text in it, exactly like an ArrayList. Appending writes into the spare room — no new object, no copying — until the array fills up, at which point it grows to (old × 2) + 2.

  • new StringBuilder() → capacity 16.
  • new StringBuilder("Gsec") → capacity str.length() + 16 = 20.
  • new StringBuilder(100) → capacity exactly 100.
  • Growth: newCapacity = (oldCapacity << 1) + 2 → 16 → 34 → 70 → 142 → 286 …

💡 Which one for the exam answer?

StringBuilder, unless the buffer is genuinely shared between threads — which is rare, because a builder is normally a local variable, and local variables cannot be shared. StringBuffer pays a locking cost on every single call for a guarantee almost nobody needs.

replace vs replaceAll vs replaceFirst

The one-character difference that changes everything

replace() takes literal text. replaceAll() and replaceFirst() take a regex. So "a.b".replace(".","-") gives a-b, while "a.b".replaceAll(".","-") gives --- — because . means "any character".

Comparing strings — four methods, four different answers

What compareTo actually returns

Not just −1/0/1. It walks both strings and returns this.charAt(i) - other.charAt(i) at the first difference. If one is a prefix of the other it returns the length difference. Output questions love this — "Apple".compareTo("Banana") is 'A'-'B' = −1, but "a".compareTo("A") is 32.

Dates as strings

Every date in a file, a form or a database arrives as text

A date is not a string, and a string is not a date. All real work therefore happens at the two boundaries: parse (String → date object) and format (date object → String). Get the pattern wrong and you either crash or, worse, silently get the wrong answer.

The modern API — java.time, since Java 8

  • LocalDate — a date with no time and no zone. Use this for a date of birth or an admission date.
  • LocalTime, LocalDateTime — time only, and both together.
  • DateTimeFormatter — immutable and thread-safe.
  • Period / ChronoUnit — for "how old is this student".

The legacy API — still all over exam papers

  • java.util.Date — a millisecond count pretending to be a date.
  • SimpleDateFormat — not thread-safe; sharing one across threads corrupts output.
  • Calendar — months are 0-based, so January is 0.
  • Know it, name its problems, then use java.time.

⛔ The two traps that cost the most marks

1 · mm instead of MM. "dd/mm/yyyy" compiles, runs, and prints the minutes where the month should be. On 14 July at 09:05 it prints 14/05/2026 — a plausible-looking wrong date, which is the worst kind of bug.
2 · YYYY instead of yyyy. Capital Y is the week-based year. For most of the year it matches, then in the last days of December it jumps to the next year — a bug that appears once a year and is impossible to reproduce in July.

Packages

A folder for your classes, and a namespace for their names

A package does three jobs: it groups related classes, it prevents name clashes (your Date and Java's Date can coexist), and it defines the access boundary that default and protected are measured against — which is why tab ⑦ cannot be explained without this one.

Two kinds

  • Built-in — shipped with the JDK: java.lang, java.util, java.io, java.time.
  • User-defined — yours: com.gsec.model, com.gsec.util.

Three rules that are always tested

  • The package statement must be the very first line of code — comments above it are fine, nothing else.
  • The folder structure must match the package name, segment for segment.
  • java.lang is imported automatically; that is why String and System need no import.

The naming convention, and why

All lowercase, reverse domain name first: com.company.project.layer. Reversed because domains are globally unique, so no two organisations can ever collide.

The default package

A file with no package statement lands in the unnamed package. It works for exercises but a packaged class can never import from it — which is why your Gsec.java cannot be reused from anywhere else as it stands.

import — what it does and does not do

  • It is not #include. Nothing is copied. import only lets you write Gsec instead of com.gsec.model.Gsec.
  • The wildcard costs nothing at runtime. import java.util.*; is not slower — it is resolved at compile time. It only risks ambiguity, e.g. java.util.Date and java.sql.Date both imported.
  • It does not reach into sub-packages. import com.gsec.*; does not bring in com.gsec.model.
  • Static import brings in members, not types: import static java.lang.Math.PI; then just PI.
  • Ambiguity is your problem. Import both Dates and the compiler makes you use a fully qualified name.

The mistake everyone makes once

Running java Gsec from inside the model folder. A packaged class must be launched from the root of the package tree, by its fully qualified name: java com.gsec.model.Main. Otherwise you get NoClassDefFoundError: Gsec (wrong name: com/gsec/model/Gsec).

Access specifiers

Four levels, measured against the package boundary

Access control is not about secrecy — it is about who you promise not to break. A public field is a promise to the entire world; a private one is a promise only to yourself. Your Gsec class already makes exactly one of those promises correctly.

Two rules about the class itself

A top-level class can only be public or default — never private or protected. And a public class must live in a file with a matching name. Nested classes, by contrast, may use all four.

⛔ protected is subtler than it looks

A subclass in a different package can access protected members through its own inheritance — this.age or super.age — but not on an arbitrary instance of the parent. new Gsec().age from that subclass is a compile error even though this.age is fine.

What to actually write

Fields

private, almost always. Expose them through getters. Your age is right; name, laptop and registerNumber are not.

Methods

public if the method is part of what the class offers; private for internal helpers. Your validator() and display() are default — usable only inside the package, which is probably accidental.

Constants

public static final is fine, because an immutable value cannot be broken by anyone.
