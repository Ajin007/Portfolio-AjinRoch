01 · Anatomy

One String, three pieces of memory

A variable on the stack holds a reference. The String object on the heap holds a header: a pointer to the character array, a one-byte coder flag, and a cached hash. The characters themselves live in a final byte[] that no method ever writes to.

COMPACT STRINGS · JAVA 9+

Before Java 9, the backing store was a char[] — two bytes per character even for plain ASCII. Java 9's Compact Strings switched to a byte[] plus a coder flag: LATIN1 (1 byte/char) when possible, UTF16 (2 bytes/char) only when needed. Typical apps cut String heap usage dramatically.

THE hash FIELD

Immutability makes caching safe: the first hashCode() call computes h = 31·h + c across the characters and stores it. Every later call is a field read — which is exactly why Strings are the default HashMap key. Watch the computation animate in the hashCode lab.

04 · hashCode lab

h = 31·h + c, animated

String's hash is a rolling polynomial: start at 0, and for each character multiply by 31 and add the char code (32-bit wrap-around). 31 is odd and prime — good bit mixing — and 31·h compiles to a cheap (h<<5)−h. The result is cached in the hash field forever.

05 · Builder lab

StringBuilder: the mutable one

A StringBuilder is a non-final char buffer plus a count. Appends write in place; when the buffer fills, it grows to oldCapacity·2 + 2 and copies once. That amortized growth is why a loop of appends is O(n) while a loop of + is O(n²).

The buffer starts at capacity 16 (new StringBuilder() with no seed). Append text and watch count advance; overflow the capacity to trigger a growth event: newCap = old·2 + 2, one full copy, then writing continues.
toString() makes a snapshot. It copies buffer[0..count) into a new immutable String. Appending afterwards does not change the snapshot — builder and String are decoupled the moment toString returns.

== vs equals() vs compareTo() — the decision rule

Use == only to test whether two variables point at the exact same object (or for str == null). Use .equals() for business logic — checking that text content matches. Use .compareTo() only when you need ordering: sorting, ranking, or ordered structures. In a typical project, equals() covers ~95% of comparisons.

String enteredOtp = new String("1234");   // dynamic value → heap object
String correctOtp = "1234";               // literal → pool

enteredOtp == correctOtp        // false — different objects! The classic auth bug
enteredOtp.equals(correctOtp)   // true  — correct business validation

== "accidentally works" for two literals because of the pool (Memory canvas, scenario 1), then fails the moment a value arrives from a database, file, network, or new — which is why the bug survives testing and dies in production.

Null-safety — try it live

A value from a database or API can be null. Calling .equals() on it throws NullPointerException. Three patterns, ranked:

// ✗ DANGEROUS — crashes when inputStatus is null
if (inputStatus.equals("ACTIVE")) { ... }

// ✓ YODA CONDITION — the constant is never null, so this returns false instead
if ("ACTIVE".equals(inputStatus)) { ... }

// ✓ ENTERPRISE — both sides might be null
if (Objects.equals(userInput, dbRole)) { ... }

compareTo() in practice — sorting database entities

Real projects rarely sort plain strings — they sort objects by a string field. Comparator.comparing calls compareTo behind the scenes:

// Sort employees alphabetically by last name (calls lastName1.compareTo(lastName2))
employees.sort(Comparator.comparing(Employee::getLastName));
// [John Smith, Alice Brown, Bob Miller] → [Alice Brown, Bob Miller, John Smith]

// Mixed case trap: plain compareTo puts "Zack" before "alice" (uppercase < lowercase)
employees.sort(Comparator.comparing(Employee::getLastName, String.CASE_INSENSITIVE_ORDER));

// Multi-level: last name first, then first name on ties
employees.sort(Comparator.comparing(Employee::getLastName)
                         .thenComparing(Employee::getFirstName));

The uppercase-first quirk is the char-code math from the Method lab: 'Z'(90) − 'a'(97) = −7, so "Zack" sorts before "alice" unless you use CASE_INSENSITIVE_ORDER for user-facing lists.

split() playbook — it returns a String[]

split() cuts the string at every regex match, discards the delimiters, and packs the pieces into a fixed-size String[] you index into:

String csvRow = "Laptop,800,Electronics";
String[] items = csvRow.split(",");      // length 3
String productName = items[0];           // "Laptop"
String price       = items[1];           // "800"
String category    = items[2];           // "Electronics"
RISK 1 · META-CHARACTERS

The argument is a regex. . | $ * + ? ^ have special meanings — "invoice.pdf".split(".") returns an empty array because dot = any character. Escape with \\. (source form) to split on a literal dot.

RISK 2 · TRAILING EMPTIES

"John,Doe,,".split(",") has length 2, not 4 — trailing empty strings are silently discarded, and your result[3] crashes. Fix: split(",", -1) keeps every slot.

// Data-cleaning patterns
"Java    Python   C++".split("\\s+")        // any run of whitespace → ["Java","Python","C++"]
"Apple,Banana|Orange;Grape".split("[,|;]")  // comma OR pipe OR semicolon
hugeText.split(",", 2)                       // only need the first piece? stop after 1 cut

HOT LOOPS · Pattern.compile

Every s.split(regex) call compiles the regex again. Parsing a million log lines? Compile once, reuse forever — and splitAsStream feeds pipelines directly:

static final Pattern COMMA = Pattern.compile(",");

for (String line : millionLines) {
    String[] cols = COMMA.split(line);  // no re-compile
}

COMMA.splitAsStream(csvRow)              // Stream<String>
     .map(String::trim)
     .filter(s -> !s.isEmpty())
     .toList();
ARRAY → LIST / STREAM

The String[] is fixed-size. Convert it when you need collection behavior:

String[] parts = csv.split(",");

List<String> view = Arrays.asList(parts);
// fixed-size VIEW — add() throws UnsupportedOperationException!

List<String> list = new ArrayList<>(Arrays.asList(parts));
// truly mutable copy

Arrays.stream(parts).map(String::trim).toList();
// straight into a Stream pipeline
LEGACY · StringTokenizer

You'll meet it in old codebases. It splits on characters (not regex) and silently skips empty tokens — so it can never do fixed-column parsing:

StringTokenizer st = new StringTokenizer("a,,b", ",");
st.countTokens();   // 2 — the "" vanished
// split(",", -1) → ["a","","b"] length 3 — trustworthy
// JavaDoc itself says: prefer split / java.util.regex
REAL CSV & NEWLINES

Two boundaries where naive split breaks:

// Quoted commas defeat split:
"Laptop,\"1,299\",Electronics".split(",")
// 4 pieces, price torn apart → use a CSV library
// (OpenCSV / Commons CSV) for real CSV files

// Cross-platform line splitting (\n vs \r\n):
fileText.split("\\r?\\n")
// or Java 11+: fileText.lines() → Stream<String>

Code-review checklist

  • Length before index: verify parts.length > 2 before touching parts[2] — trailing-empty removal makes lengths shorter than they look.
  • Null before split: a null base string throws NPE before the regex is even parsed.
  • Yoda or Objects.equals for every comparison against data that came from outside the JVM.
  • limit for performance: split(",", 2) when you only need the head of a massive string.
  • CASE_INSENSITIVE_ORDER for any user-facing alphabetical list.
