What exception handling is, and why it exists

Exception handling is Java's mechanism for dealing with runtime errors so a program can continue operating or terminate gracefully. It separates error-handling code from regular logic, which keeps both readable and maintainable. Without it, one bad input crashes the whole application.

The cashier analogy. When a product barcode doesn't scan, the cashier doesn't close the store — they type the code manually or call for help. That's exception handling: the unexpected happens, a defined recovery path runs, and business continues. (Analogy from Shant Khayalian's guide — see references in the footer.)

The five keywords — click each to expand

try

Wrap risky code

The block where an exception might occur. If one is thrown, remaining statements in the block are skipped and control jumps to a matching catch.
catch

Handle the failure

Handles a thrown exception by type. Multiple catch blocks are checked top to bottom — put subclasses before superclasses or the later one becomes unreachable (compile error).
finally

Always runs

Executes whether or not an exception was thrown — perfect for cleanup like closing files or connections. Skipped only by System.exit() or a JVM crash.
throw

Raise one, now

Explicitly throws a single exception object: throw new IOException("File not found");. Used inside method bodies.
throws

Declare on method

Goes on the method signature to declare checked exceptions the method may propagate: void readFile() throws IOException. It warns callers; it does not handle anything.

What the JVM actually does when a throw happens

  1. Object creation — an exception object is instantiated with the error type, message, and program state.
  2. Stack unwinding — the JVM starts at the throw point and walks up the call stack, method by method, looking for the first matching catch. Each unmatched frame is popped.
  3. Handling or death — if a match is found, that catch runs, then finally, then normal flow resumes after the try structure. If nothing matches all the way up, the thread terminates and the JVM prints the stack trace.
  4. Garbage collection — objects abandoned during unwinding are marked for GC, so handled exceptions don't leak memory.

Creating a custom exception — the 4-step pattern

CustomException.java
// 1. extend Exception (checked) or RuntimeException (unchecked)
class InvalidAgeException extends Exception {
    public InvalidAgeException(String message) {
        super(message);          // 2. store message via superclass
    }
}

static void validate(int age) throws InvalidAgeException {
    if (age < 18)
        throw new InvalidAgeException("Age is not valid to vote");  // 3. throw
}

try {
    validate(15);
} catch (InvalidAgeException e) {
    System.out.println(e.getMessage());   // 4. catch and read the message
}

Best practices (the ones graders and code reviewers both check)

DO
  • Catch specific exceptions, not a blanket Exception
  • Use finally (or try-with-resources) for cleanup
  • Keep the exact expected message in super(msg); add prefixes like "Error: " in the catch
  • Document thrown exceptions with JavaDoc
DON'T
  • Leave empty catch blocks — that's exception swallowing
  • Catch Error or use exceptions for normal control flow
  • Put the superclass catch before the subclass (unreachable code = compile error)
  • Print e.getMessage() when the grader expects the class name — that prints null for InputMismatchException
